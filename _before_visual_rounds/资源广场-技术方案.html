1需求概述与可行性评价

1.1 需求拆解

需求具体要求技术判断难度
R1 资源广场集中存放并展示 PPT 课件，供用户浏览需新增资源列表页与课程数据源中
R2 只能播放用户可在线查看，但无法下载源文件必须由服务端渲染成图片，源文件永不外发高
R3 修改意见用户可对 PPT 内容提出修改意见表单 + 数据持久化，依赖后端接口低
R4 后台可见意见数据在后台管理端可查看与处理需管理端页面 + 意见数据表中
核心结论

R2 与 R3/R4 三个需求都指向同一个前提：必须引入后端服务。现有纯静态架构无法满足——只要原始文件能被浏览器请求到，就一定能被下载；而意见数据也需要持久化。好消息是，这两件事正好与"后续开发后台"的计划合并推进，一次投入即可满足全部需求。

1.2 能力边界（必须提前对齐）

"不能被下载、只能被播放"在技术上没有 100% 的阻断方案，业界（包括各类在线课件平台）均采用"提高成本 + 水印追责"的策略。建议在需求确认阶段就把目标表述为下表右列的形式。

✅ 可以做到❌ 无法做到
不提供下载入口，用户拿不到原始 PPT 文件阻止用户截屏、拍照或录屏
每页图片叠加"用户 ID + 时间戳"水印阻止用户保存图片后二次传播
短时效签名 URL、禁右键、禁拖拽阻止技术人员从浏览器网络面板抓取
存储目录不可浏览，源文件置于私有存储——
全程操作审计，泄露内容可溯源追责——
⚠ 建议的需求表述

把"PPT 不能被下载"改写为："不提供下载入口 + 显著提高获取成本 + 全程水印可追责"。提前对齐这一点，可以避免后期验收时因"用户仍能截屏"而产生争议。

2技术栈选型

选型原则：沿用现有技术基因（原生 H5、零框架），只在"必须新增"的地方引入依赖，降低团队学习成本与部署复杂度。

层次推荐选型选择理由
前端沿用原生 HTML / CSS / JS，新增 resources.html与现有页面风格与代码习惯完全一致，无需引入框架
后端Node.js + Express
（备选：Python FastAPI）		与前端同语言，团队上手快；若更侧重图像处理也可选 FastAPI
PPT 转换LibreOffice headless → PDF → 逐页 PNG开源免费、跨平台、效果稳定，是业界事实标准
转换备选PowerPoint COM（保真最高）／ Aspose.Slides（付费）仅在保真度要求极高时才采用，成本与复杂度都更高
图像处理sharp（水印 / 压缩 / 切片）Node 生态中最成熟的图像库
对象存储MinIO（自建免费）／ 阿里云 OSS、腾讯云 COS源文件放私有桶，切片图放受控桶，天然隔离
数据库SQLite（起步）→ MySQL / PostgreSQL起步零配置，数据量增长后平滑迁移
部署Docker Compose（nginx + api + worker + minio + db）一个文件拉起全套环境，最省心的方案
过渡方案Supabase（自带 Postgres + Storage + 可视化后台）后台未完成期间可立刻看到收集到的意见，后期再迁回自建

3核心实现要点

3.1 防下载的分层策略（按性价比排序）

  1. 源文件永不出域：原始 .pptx 只存放在私有存储桶中，仅转换服务可读；前端自始至终只接触渲染好的 PNG 切片。这是整个方案的技术根基。
  2. 签名 URL：GET /slides?token=xxx，token 为短时效（约 10 分钟）JWT，绑定用户与 PPT 编号，过期立即失效。
  3. 服务端水印：每页图片在服务端叠加"用户 ID / 昵称 + 时间戳"平铺半透明水印。这是真正有价值的一层——防不住下载，但一旦外泄可精准溯源追责。
  4. 前端软防护：禁用右键菜单、user-select:none、-webkit-user-drag:none，并使用 <canvas> 逐页绘制而非直接使用 <img>，提高抓取门槛。
  5. 高清渲染：按 150–200 DPI 渲染切片，保证放大后文字依然清晰可读。
  6. 服务端加固：关闭目录浏览（Nginx 禁用 autoindex），响应头设置 Content-Disposition: inline，禁止外部站点盗链。

3.2 修改意见模块

  • 基础字段：PPT 编号 + 页码 + 意见内容 + 联系方式（选填）。
  • 进阶玩法（推荐）：允许用户在幻灯片上框选区域后再提交意见，后端存储归一化坐标 [x, y, w, h]（取值 0–1，与分辨率无关）。后台即可精准定位到"第 5 页左上角那个数据有误"，这是本功能真正的差异点。
  • 状态流转：提交后进入意见表，后台按"待处理 → 已采纳 / 已驳回"流转，并记录处理人与处理时间。

3.3 过渡期方案：适配器模式

后台尚未开发完成时，前端不应被阻塞。通过统一的 FeedbackService 接口 + 可替换实现，后期切换只改一行配置，业务代码零改动。

// 统一接口：业务层只依赖这一层
FeedbackService.submit({ pptId, page, area, content, contact })

  ├─ LocalStorageAdapter   // 现在：暂存本地，支持"导出 JSON"
  ├─ SupabaseAdapter       // 过渡：直接落库，后台可即时可见
  └─ HttpAdapter           // 后台就绪：fetch POST /api/feedback

推进建议

一期与二期可以并行推进：前端按第 3.5 节的接口契约先行开发并用 LocalStorage 适配器跑通交互，后端就绪后只需替换适配器即可，不会产生返工。

6风险与注意事项

  • 预期管理风险（最高）：需求方若坚持"绝对无法下载"，会与验收标准冲突。务必在开工前书面确认第 1.2 节的能力边界。
  • 转换保真度：LibreOffice 对复杂动画、特殊字体、SmartArt 的还原度有限。建议制定一份课件制作规范（如统一使用常见字体），或在关键课件上改用 PowerPoint COM。
  • 性能与成本：200 DPI 切片体积较大，建议按需懒加载、开启 CDN 缓存；转换任务务必异步化，避免阻塞接口响应。
  • 版权合规：上传的 PPT 需确认来源合法，后台应保留上传者与授权记录。
  • 水印隐私：水印包含用户标识，属个人信息，需在隐私政策中说明用途并限制访问权限。
  • 文件命名隐患：现有项目原有 index .html（文件名含空格）与 class.html（首页）两个易混淆的文件，且 logo 链接指向不存在的 index.html。已处理：现已整理为 index.html（课程列表首页）+ course.html（课程详情），全站引用同步更新。新增页面请沿用这一无空格的英文命名规则。
